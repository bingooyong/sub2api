# Frontend Build Toolchain

> Contracts for installing and building this repository's frontend with pnpm 11.

---

## Scenario: pnpm 11 moved `pnpm.*` settings out of package.json

### 1. Scope / Trigger

Read this contract when you:

- run `pnpm install` / `pnpm run build` for this repository;
- add or change a dependency override;
- hit `ERR_PNPM_IGNORED_BUILDS` or `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`;
- produce a release build whose `backend/internal/web/dist` is used by the
  server image.

Triggered because pnpm 11 stopped reading the `pnpm` field of `package.json`.
The overrides silently stop applying, and the build either refuses to run
(build scripts blocked) or fails the lockfile check.

### 2. Signatures

```bash
# canonical install
cd frontend
pnpm install --frozen-lockfile     # requires pnpm-workspace.yaml to carry overrides
pnpm run build                      # check:i18n -> vue-tsc -b -> vite build
```

Build output location (fixed by `frontend/vite.config.ts`):

```ts
build: { outDir: '../backend/internal/web/dist' }
```

**Current repository state**: the overrides live in **both** places, with
byte-identical content:

- `frontend/package.json` → `pnpm.overrides` (read by pnpm 10 and earlier);
- `frontend/pnpm-workspace.yaml` → `overrides` + `onlyBuiltDependencies`
  (read by pnpm 11).

Keeping both is intentional: pnpm 10 ignores the workspace file, pnpm 11
ignores the `pnpm` field, and both resolve the same dependency set. CI uses
`pnpm/action-setup@v6` **without pinning a version**, so it may run pnpm 11 at
any time — the workspace file is what keeps the build working there.

For a pnpm 11 build, provide a `frontend/pnpm-workspace.yaml` containing the
same overrides plus the build-script allowlist:

```yaml
overrides:
  "js-cookie": "3.0.7"
  "form-data@<4.0.6": ">=4.0.6"
  "postcss@<8.5.18": ">=8.5.18"
  "dompurify@<3.4.17": ">=3.4.17"
  "source-map-js@<1.2.2": ">=1.2.2"
  "follow-redirects@<1.16.1": ">=1.16.1"

onlyBuiltDependencies:
  - esbuild
  - vue-demi
```

> Measured 2026-10-23: even with the overrides migrated verbatim, pnpm 11 still
> reported `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` against the existing
> `pnpm-lock.yaml` (which was generated by pnpm 10). The lockfile's recorded
> override normalization does not round-trip through pnpm 11. The working
> procedure is therefore `--no-frozen-lockfile` **plus** an explicit assertion
> that the pinned versions actually landed (see Tests Required). Do not treat
> a successful build alone as proof that the overrides applied.

### 3. Contracts

1. **The `pnpm` field of `package.json` is not read by pnpm 11.** It is
   ignored, with a warning:
   `The "pnpm" field in package.json is no longer read by pnpm.`
   Overrides must live in `pnpm-workspace.yaml`.
2. **The lockfile's override check does not survive the pnpm 11 migration.**
   `pnpm install --frozen-lockfile` compares the current overrides against the
   set recorded in `pnpm-lock.yaml`; with pnpm 11 reading the overrides from
   `pnpm-workspace.yaml` the comparison fails with
   `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` even when the values are identical,
   because the lockfile was written by pnpm 10. Consequence: **on pnpm 11 the
   frozen-lockfile guarantee is unavailable, and the overrides must be verified
   by asserting the installed versions instead.**
3. **Build scripts are blocked by default.** `esbuild` and `vue-demi` need
   their install scripts, so they must be listed in
   `onlyBuiltDependencies`. Without it the install fails with
   `ERR_PNPM_IGNORED_BUILDS`.
4. **YAML keys containing `@` or `<` must be quoted.**
   `"form-data@<4.0.6": ">=4.0.6"` — unquoted, the YAML parser chokes on
   `<` and the whole settings file fails to load.
5. **Regenerating the lockfile changes the resolved dependency set.** With
   pnpm 10 and a matching lockfile, prefer `--frozen-lockfile`. With pnpm 11
   the lockfile check is unusable (contract 2), so `--no-frozen-lockfile` is the
   practical path — and the pinned versions must then be asserted explicitly.
   A regenerated lockfile is **not** part of the release artifact, but it must
   not be committed silently either: it changes what CI and other developers
   install.
6. **The built `dist` is part of the release artifact.** It is embedded into
   the Go binary via `//go:embed all:dist`, so a stale `dist` produces a
   server image whose UI does not match its backend.

### 4. Validation & Error Matrix

| Condition | Required result |
| --- | --- |
| `ERR_PNPM_IGNORED_BUILDS` (esbuild / vue-demi) | Add the package to `onlyBuiltDependencies` |
| `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` | The pnpm 10 lockfile's override normalization does not round-trip through pnpm 11 → use `--no-frozen-lockfile` and assert the pinned versions landed |
| Warning `"pnpm" field ... is no longer read` | Expected on pnpm 11; do not "fix" it by editing `package.json` |
| YAML parse error near a key with `@<` | Quote the key and the value |
| `vue-tsc` reports missing types | The install was incomplete; re-run the install, do not build on a partial `node_modules` |
| `dist/` is missing or stale | The build did not run or ran on a different source tree; rebuild from the same snapshot as the binary |

### 5. Good/Base/Bad Cases

- **Good**: `pnpm-workspace.yaml` carries the overrides verbatim plus
  `onlyBuiltDependencies`; `pnpm install --frozen-lockfile` succeeds; the build
  produces `backend/internal/web/dist` from the same source snapshot as the
  binary.
- **Base**: the only build-script consumers are `esbuild` and `vue-demi`; the
  allowlist stays short on purpose.
- **Bad**: keeping the overrides in `package.json` only. The install either
  fails the lockfile check or resolves different versions, and the security
  pin (`dompurify`) silently disappears from the artifact.

### 6. Tests Required

- `cd frontend && pnpm install` → must exit 0 with no `ERR_PNPM_*` output
  (use `--frozen-lockfile` on pnpm 10, `--no-frozen-lockfile` on pnpm 11).
- `cd frontend && pnpm run build` → must produce `backend/internal/web/dist`
  containing `index.html` and `assets/`.
- Assert **every** pinned version actually landed, e.g.
  `node -e "console.log(require('./node_modules/dompurify/package.json').version)"`
  → `3.4.17`. This assertion replaces the frozen-lockfile guarantee and must
  not be skipped on pnpm 11.
- A release build must be produced from the **same source snapshot** as the
  server binary; verify the asset filename referenced by `index.html` changes
  when the frontend changed and does not change when it did not.

### 7. Wrong vs Correct

Wrong: rely on `package.json` alone

```json
{ "pnpm": { "overrides": { "dompurify@<3.4.17": ">=3.4.17" } } }
```

pnpm 11 ignores this block; the override is not applied and
`--frozen-lockfile` fails with `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`.

Wrong: assume "the install succeeded" means "the overrides applied"

```bash
pnpm install --no-frozen-lockfile && pnpm run build   # overrides may not have applied
```

Correct: provide the settings where pnpm 11 reads them, and assert the result

```bash
# frontend/pnpm-workspace.yaml carries the overrides + onlyBuiltDependencies
pnpm install --no-frozen-lockfile
node -e "console.log(require('./node_modules/dompurify/package.json').version)"  # must be 3.4.17
pnpm run build
```

Correct: `pnpm-workspace.yaml`

```yaml
overrides:
  "dompurify@<3.4.17": ">=3.4.17"

onlyBuiltDependencies:
  - esbuild
  - vue-demi
```

Wrong: pipe a critical command and trust the exit code

```bash
pnpm install --frozen-lockfile | tail -4   # exit code is tail's, not pnpm's
```

Correct: run it unpiped, or check `PIPESTATUS[0]`

```bash
pnpm install --frozen-lockfile
```
